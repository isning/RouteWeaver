## 已复现问题与决定

缓存列表中的 Output A 仍是已发布状态；后台在预览之前撤销它，清空 token。预览正确捕获当前 Output B，之后发布也正确通过摘要与比较写入，却会签发新链接。旧界面的“链接不变”、确认动作和成功后的获取分支仍由 A.status 推导。因此既有发布 fence 没有失效，错误在于用户批准的后果与该次审阅实际状态不同。

项目综合规则：**确认后果必须来自动作所批准的同一份权威快照，不以缓存列表生命周期代替。** 这不是外部指南规定 DTO 结构，也不是 Google 认证或真人理解研究结论。

- owner-only 的 `output-update` 预览新增 `publicationEffect: {version:1, link:"preserve"|"replace"}`，根据捕获对象的 token 是否为空推导，与发布的签发条件一致。不暴露 token/链接；不改变身份、target、mode、兄弟订阅、撤销策略或自动发布规则。
- 现有 SHA256 摘要已经包含捕获对象的 token 状态；不是 HMAC。撤销不改变渲染 revision，单独加 expectedRevision 不能解决本例。
- 新界面先核对 outputId、用途及摘要，再显示兼容性、路由或技术内容；错对象/用途/摘要的响应只显示检查失败。已绑定但后果缺失、损坏或版本未知时不猜测，阻止确认，保留本地重新检查和取消。
- 检查前不承诺链接结果。检查后后果与确认按钮同处页脚：保留时“链接不变，其他订阅不受影响。”；签发时“将生成新的访问链接。其他订阅不受影响。” 不据签发决定推断损坏历史记录的旧链接健康，也不把配置包一律说成重加订阅。
- 点击时复制批准的对象、名称、摘要、后果和任务代次。成功后以该副本决定获取分支；暂停、关闭或任务替换使迟到界面延续失效，已成功的服务端写入仍使正确对象缓存失效。409要求重新检查；网络失败不自动再写。

旧 API 客户端可忽略新增字段，原发布参数兼容。新版 UI 遇到不提供后果的旧服务端会阻止确认，这是明确的兼容边界，不以猜测或全页刷新绕过。
