# Server-owned agent and independently managed cores

The agent belongs to a physical server. A server can enroll before it has any core instances. One foreground agent discovers the server's core assignments and runs an isolated reconciliation lane for each core. Adding a core does not require enrolling another agent.

## Ownership and authority

- `Host` owns the agent enrollment. The root credential is scoped to that host and enrollment epoch. Root routes provide private assignments and accept physical-resource reports.
- `CoreInstance` retains independent desired generations, configuration revisions, leases, observations, meters, diagnostics and runtime journals. These execution scopes are internal to the server agent; they are not separate installation steps for the operator.
- Child credentials are derived using a private server-side derivation key. Public inventory and agent-state views do not expose credentials or the key. The host assignment response is authenticated and non-cacheable.
- Enrollment rotation revokes the previous root and all its child credentials atomically. Revocation and expiry invalidate both levels. A moved core loses access through its old server and receives authority from its new server only when that server has an active enrollment.
- Membership and record comparisons fence enrollment, assignment publication and core installation against concurrent inventory changes. Current bounded manifests allow at most 64 cores per host.
- Existing instance enrollment remains available only for servers without a host enrollment. Once a server adopts host enrollment, individual instance re-enrollment is rejected. Existing persisted instance journals are not silently re-used under a different authority.

## Runtime and installation

`node-agent --mode host --service` requires a private token file, host ID, enrollment epoch, private state directory and core store. Use the command generated by the server's enrollment dialog. All remote traffic is outbound and verified HTTPS; literal loopback HTTP is an explicit test-only option. No inbound shell or agent management port is introduced.

The server overview owns the enrollment action. A core's page owns its installation action. An administrator can queue a reviewed, exact catalog release before creating listeners. The first-install API uses the current desired generation as a precondition. A core that already has runtime intent uses the existing reviewed maintenance workflow rather than replacing its intent through the first-install action.

The agent downloads only pinned official catalog archives, verifies archive and executable hashes, and performs the native configuration check. The shared installer serializes local preparations while honoring context cancellation. Installation does not activate a core or create listeners. Activation still requires explicit local process opt-in and the existing reviewed deployment path. Catalog/platform availability is not universal: current remote releases are the existing approved Linux amd64 stock Xray and sing-box releases. Managed Xray requires the trusted packaged binary supplied with `--managed-xray-binary`; it is not downloaded as stock Xray.

Each child uses an enrollment-scoped private journal and durable meter outbox. Renaming a core or changing version metadata does not restart its worker. Removal cancels only that core; replacement waits for the previous worker to stop. Partial manifests and transient network failures retain the last valid assignment. Explicit authorization rejection or parent expiry stops all owned workers. Shutdown is bounded; uncertain cleanup is reported, not claimed successful.

## Physical resources

The server agent reports CPU, memory and NIC observations once per host, including servers with no cores. The resource report uses an explicit host-agent discriminator and no core instance ID. Authentication and repository ingestion both validate the active parent enrollment.

Adopting the host source from a legacy instance observer resets resource history and the NIC estimate baseline, preventing mixed-source history and double counting. Provider configuration is retained. Both enrollment and settings forms explain the reset when a legacy observer is present. Editing ordinary host-agent settings or rotating an already host-owned enrollment does not reset history merely because credentials changed.

## Boundaries

Root connectivity is not core health. A queued task is not an installed binary; an installed binary is not an activated or traffic-tested service. Real-server setup, packaging/service-manager integration, every upstream protocol option and deployed acceptance remain separate from this change.
