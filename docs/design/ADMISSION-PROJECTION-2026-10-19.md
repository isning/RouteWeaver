# Bounded admission working state, without discarding accounting evidence

Status: design only, 2026-10-19. No production implementation or performance claim. Read against the current store, its counter ingestion/recovery paths, both backup implementations, and `docs/verification/ADMISSION-SCALING-2026-10-19.md`. The aggregate verification freeze remains in force.

## Decision

Use SQLite as the durable, cross-process owner of a small encrypted **admission working-state projection**, not an in-memory cache. Keep every canonical encrypted record and existing public Store interface. First centralize tracked mutations and prove backup/restore behavior; then optimize reads. This is a medium-sized, reviewable persistence change, not a one-function optimization. An account index alone is a useful intermediate measurement, not the final fix.

Recommended first implementation deliberately omits the account membership index and leaves infrequent cold usage rebuilds linear in the full canonical ledger. An optional subsequent account index reduces that to one account's history after its completeness contract is independently reviewed. Warm admission must be independent of settled lifetime history, including no-reset accounts. If cold monthly rebuild latency becomes material, add keyed time-bucket indexes later, not a new database, custom encrypted tree, or a general event-sourcing framework now. This does not promise a hard bound for every request or unlimited fleet throughput.

## What actually grows

`AcquireAdmission` reserves SQLite's writer before eligibility and claims. Eligibility scans all holds, resets, and ledger; finite budget granting scans resets/rates again, all budgets, and ledger again; presence claims scan all leases. `effectivePolicyTx` also scans plans/groups/routes twice per admission. The measured 10,000 unrelated ledger-row result isolates only the ledger cost, not the other costs.

Two independent dimensions matter: unrelated accounts and a single account's settled history. Even an account-only index would leave two lifetime ledger reductions and lifetime lease/budget filtering per renewal. A process-local cache would additionally lose the cross-Store/process serialization guarantee.

## Small private module and its state

Add private transactional helpers, conceptually `admissionStateTx(account, now, window)` and tracked record write/delete helpers. Callers do not manage cache generations. Keep policy evaluation live and canonical rather than caching resolved service/group policy.

Separate rebuildable tables from `records`:

- Optional later stage, not required for the first ledger slice: an account membership index from `(kind, record ID)` to a domain-separated keyed account token, with lookup index `(kind, account token, record ID)`. Source ownership is parsed from decrypted typed records, never inferred from ID prefixes: admission/counter ledger IDs do not share a user prefix. Derive the index key separately from the master key; do not store raw key material. Account IDs already occur in canonical cleartext IDs, so this is not anonymity, and equality/access-pattern leakage must be documented.
- One AEAD-encrypted working-state row per account, with authenticated identity/version. It contains one usage window identity and exact totals, a lease working set, reservation working state, and the time watermark used for expiry compaction. Do not put client IPs, raw/weighted usage, rates, grant credentials, or policy values into index columns.
- A tiny derived-schema/version/dirty-state table and three SQLite triggers on canonical tracked INSERT/UPDATE/DELETE. These are a correctness backstop for generic writers and future missed paths, not the main incremental algorithm.

Do not silently put observed timestamps, IPs, quotas, or budget amounts into SQL columns to gain indexing. Plaintext timestamp/expiry indexes would be simpler and faster, but disclose additional activity metadata. They are an alternative requiring an explicit privacy/design decision, not part of this recommendation.

### Usage window

Persist `{start, end-or-unbounded, raw total, provider total, exact weighted numerator}` encrypted. Raw/provider totals must also be stored losslessly: a total exceeding the read interface must remain a read error, not truncate or reject a canonical meter write that previously succeeded. The numerator is the exact sum of `RawBytes * RateMicros`, represented losslessly using `big.Int` decimal text. Round up once at read, just as `aggregateUsageRecords` does. Never sum per-row `WeightedBytes`, use floating point, or rely on SQLite INTEGER/SUM for the numerator.

A ledger insert into an existing clean stored half-open window adds its exact contribution in the same transaction. If the account projection is absent, leave it absent: never initialize its total from only the newly arriving delta. Its first read must reconstruct the complete canonical window. A replacement subtracts the old contribution and adds the new; an owner change updates both owners. Deletion reverses the contribution. Replays with unchanged payload are neutral. Use arbitrary precision internally and preserve the current overflow/error behavior when converting externally visible totals; do not truncate an oversized numerator.

The membership decision is based on frozen `ObservedAt`, not commit time, `RecordedAt`, or request arrival. No-reset end remains unbounded. Finite windows include all committed facts before calendar end, including facts later than the waiting request's `now`; the existing code intentionally does not cap usage at arrival time. Late settlement still uses the existing expiry-minus-one-nanosecond attribution. A late old-window row changes canonical history and indexes but not the new window total.

Recompute the effective policy, actual cycle window, and latest applicable reset on each admission. If `(start,end)` differs, rebuild this one account's window from canonical history (initially scanning the full canonical ledger; later using only a completeness-verified account index) and replace the single cached window. This also handles backwards `now`, future-dated resets becoming applicable, entitlement/calendar changes, and first group assignment. Quota/rate/route changes alone do not rewrite historical charges or require flushing a matching usage window. Historical `Usage(user,start,end)` stays exact and can use account filtering without adding an unbounded collection of cached windows.

### Leases and reservations

The encrypted lease working set holds only leases unexpired at its time watermark. Compact it during admission; never delete canonical lease records. Query/renew counts the normalized IP union and presences across **all** instances/routes for the account. A request earlier than the compaction watermark rebuilds leases from canonical account history before counting, rather than silently losing an historically active lease. This slow fallback is important because caller-supplied arrival times can go backwards after writer waiting.

Reservation state is separate from lease liveness. It tracks live relevant budgets and an expired-unresolved count, not every closed budget. A relevant budget is `!Closed && (!Finite || GrantedRaw > SettledRaw)`. Finite zero-outstanding budgets need no global reservation contribution; their canonical record still controls their own reconnect/renewal behavior. A nonfinite unclosed budget remains relevant even with zero raw outstanding. Maintain exact per-budget rounded reservation costs, not a single rounded sum of micros: current reservation semantics differ intentionally from ledger aggregation.

When time advances, move expired relevant budgets out of the live set into the unresolved count, without refunding them. Canonical budget/index records remain available for an individual settlement/review. Late settlement or final/operator resolution adjusts the count using the old budget's relevance/expiry relative to the projection watermark; a count is decremented only when that particular unresolved fact ceases to be relevant. If it remains relevant, do not decrement. A release expires only the lease and never closes/refunds the budget. Any unresolved expired budget still denies granting. For backwards time, rebuild reservation state just as for leases.

This removes closed/settled lifetime history from ordinary working state, and expired unresolved history costs one count rather than an ever-growing encrypted list. **It does not establish a fixed bound on live relevant budgets.** The 4096 presence ceiling bounds active leases only. Release expires a lease but leaves its unclosed budget relevant until settlement/expiry; repeated release/new-presence admissions can accumulate many relevant budgets with very few active leases, including unlimited and zero-rate budgets. The initial reservation projection is proportional to these genuinely outstanding obligations. Expiry compaction must still retain their unresolved count and deny as before, never refund or drop them.

Accordingly, the proposed encrypted live-budget set has a workload-dependent size and rewrite cost. For small-fleet operation this may be acceptable only after a release-churn characterization; it is not a strict bounded-state solution. Do not introduce a new reservation-count admission denial silently: that changes product semantics. An independently bounded reservation query would need indexed expiry aggregates or a separately reviewed maximum-outstanding policy. Plaintext expiry indexes are a metadata privacy choice; an encrypted ordered aggregation structure would be substantially more machinery than the ledger-first slice. Defer that stronger claim/design rather than smuggling it into this patch.

Generic/restore payloads are not validated merely by the live-presence ceiling. Malformed or oversized canonical input must fail safely, not be silently dropped. Rebuilds stream canonical account records instead of materializing lifetime slices.

Resets/rates/holds can initially use account/route-specific lookup and ordinary scans of those small relevant sets. They remain a documented residual growth path. Do not claim all history dependence is gone. A current reset lookup can be derived later if actual reset history warrants it.

## Mutation coverage and the dirty backstop

All optimized reads run after taking the existing SQLite writer reservation. Canonical writes, indexes, working state, dirty-state acknowledgment, and decision commit are one transaction. `Store.mu` alone is never the synchronization mechanism.

For tracked kinds, normal write helpers read/decrypt the old record before mutation and apply typed old/new deltas. A transaction that starts dirty must not clear the marker merely because it updated one row. Either rebuild all affected derived state under the writer reservation first, or leave it dirty and force the next optimized reader to rebuild. A clean-start tracked mutation may acknowledge only its own trigger increment after its complete derived update succeeds. Multiple writes in a batch follow this rule sequentially. Rollback rolls back every effect. Use a dirty generation rather than an unchecked boolean reset so missed earlier changes cannot be masked. Rebuild failure denies/error-outs, never uses old totals.

A global dirty fallback is intentionally coarse but small. For the first usage-only slice, a bypass causes every derived usage-window row to be invalidated/deleted transactionally before the marker is acknowledged; the requesting account is rebuilt lazily from the full canonical ledger. No membership-index rebuild is necessary. This prevents one reconstructed account from making stale totals for other accounts appear clean. A future index-bearing variant would also rebuild/validate that index before clearing dirty state. Normal ingestion must use the incremental helpers. Repeated generic production writes left on the fallback would destroy performance and must fail acceptance tests. No asynchronous invalidation or background worker is needed.

Required audit inventory:

- `AcquireAdmission`, `settleAdmissionBudget`, `grantAdmissionBudget`, `ReleaseAdmission`, `ResolveAdmissionBudget`: ledger, budgets, leases; anomalous evidence also creates accounting holds.
- `RecordMeter`: currently calls nontransactional `put` after replay/rate reads. Move its tracked mutation and replay check into the writer transaction; do not add a post-commit projection write.
- `AcceptCounterBatch`: local `put` closure directly executes SQL, and hold removal is raw DELETE. Convert these; preserve counter/ledger/cursor/receipt atomicity and admission-budget mode's prohibition on duplicate ledger charges.
- `pendingCounterBatch`: holds through `putTx`; its history-only INSERT OR IGNORE remains canonical evidence. `EstablishCounterBaseline` writes no usage and must not fabricate any projection charge.
- `ManualReset`, `SetRate`, `PutUser`, `PutServicePlan`, `PutEntitlement`, `ApplyPolicyChange`, `initializeGroupCycles`: retain all existing budget/active-limit guards. Live policy resolution avoids a service/group invalidation graph. `PreviewPolicyChange` rolls derived effects back with its preview transaction.
- `Put`/internal `put`, `PutImmutable`, `Remove`, `TenantPut`/`TenantRemove`, `UpdateRecords`, `GenerateRecord`, `CompareAndPutRecords`/`CompareSetsAndPutRecords`, `CompareSetsAndGenerateRecord`, `ComparePolicyAndPutRecords`: all accept generic kinds or associated writes. Their direct SQL cannot be ignored. Preserve their public semantics; track known kinds centrally, leave other kinds untouched.
- Raw identity/account and legacy `RecordUsage` updates change live-read user/account policy, not canonical ledger totals. They do not charge the new usage projection. `Delete` of a user must not delete its historical records or refund anything. MFA/session/token writers do not alter tracked ledger/budget/lease state, but generic token-record helpers must remain covered if used with a tracked kind.
- `ImportSnapshot` and `ImportBackup` bypass write helpers intentionally and must explicitly rebuild/invalidate derived state. Fresh restore additionally reopens a Store with a literal struct, so do not depend on `Open` alone to initialize correctness.

Use a source-level guard/test for new raw mutations outside the allowlisted persistence/import helpers. Trigger tests deliberately bypass the helpers to prove the fail-safe path. Mixed old/new binaries should not be a supported deployment mode; the triggers keep new-reader accounting safe from missed writers but do not make old code understand new schema or operations.

## Backup, migration, and immutable restore

Current backup validation allowlists exactly five physical tables and validates their columns; adding a table without updating that validator breaks backup. Explicitly classify the new derived tables and triggers as known rebuildable schema. Do not generally weaken rejection of unknown tables.

Keep canonical backup records, identities, tokens, counters, and migration rows unchanged. Exclude derived rows from the logical archive/digest by design, not accidentally. They contain no independent user fact. Keep derived-schema version in its own excluded table, not as a new canonical migration row that appears during restore and breaks `RestoreBackupFresh`'s before/after frame hash. New logical archive version is unnecessary if its canonical representation is unchanged; old archives stay readable by the new binary. Document that old binaries may reject the new physical schema.

On upgrade: stop writers, back up, create derived schema transactionally, install triggers, mark dirty, verify the key/canonical records, initialize all usage projections as absent (and rebuild verified membership indexes only if that optional stage exists), and enable optimized reads only after success. A crash leaves either no migration or durable dirty state. On reopen, verify schema/version and consult the durable marker, not a process-local initialization flag. An explicit rebuild path discards only derived state and can be repeated.

On either import: authenticate and validate the full canonical input, keep destination freshness/no-overwrite guarantees, then invalidate all derived usage windows or leave a mandatory dirty marker before committing/publishing; only the optional index-bearing stage also reconstructs its verified membership indexes. On fresh restore, canonical streamed digest equality must still succeed even when the destination master key differs. If optional keyed indexes exist, recompute them under that destination key. Checkpoint/fsync/no-replace publication stay unchanged. Imported derived totals are never trusted. Preserve unknown canonical record kinds and all unresolved/history rows.

### Explicit derived-crypto initialization contract

Derive the keyed-index secret from the supplied master key with a fixed, versioned, domain-separated standard KDF/PRF; use a separate domain for account versus any later route/time tokens. Never hash low-entropy account IDs without a secret. Store the key only in memory. Seal derived payloads with fresh nonces under the derived-state key and length-delimited AAD identifying derived kind, schema version, and account identity/token; do not reuse a canonical record's ciphertext/AAD. Reuse the existing standard AEAD algorithm, not a new homegrown cipher. Leave canonical seal/open ciphertext and key derivation unchanged.

Every Store construction path that can read/write derived state must receive the same initialized crypto context. In particular, the literal `Store{db: db, aead: s.aead}` in `RestoreBackupFresh` cannot remain unchanged if the Store gains an index-key field. Prefer one private constructor/context rather than several optional fields callers might forget. Missing context must return an error, never derive tokens with an empty key or silently skip projection validation. A different-key restore reconstructs all keyed tokens and derived payloads from canonical plaintext inside the authenticated restore flow. No derived key appears in backup frames.

The **first ledger slice omits membership indexes entirely**. A missing account projection, unsupported derived version, or durable dirty marker forces a complete canonical-ledger scan before a new window total can be used. This is the smallest way to avoid incomplete-index undercount while removing all warm settled-ledger scans. A full scan is explicitly an accepted cold-path cost, not hidden behind a latency claim.

If the optional account index is added, completeness cannot be inferred from a clean marker alone. Require an AEAD-authenticated expected canonical-row count for each account/kind; unique `(kind,record ID)` membership entries; canonical record authentication under that exact kind/ID; parsed-owner equality; and an exact count match during cold reconstruction. Update counts and index membership within the same canonical mutation/dirty transaction. Absent expected-count metadata never means zero: rebuild globally or return an error. Missing index schema, unsupported version, missing canonical target, wrong owner, or count mismatch triggers rebuild/error before a total is used. If the working-state row alone is absent, rebuild only through this completeness-verified index (or full canonical scan). These checks add work only to already-linear cold reconstruction, not each warm admission.

The supported integrity scope is accidental missing/corrupt/stale derived state and missed canonical writers. Do not claim rollback/truncation resistance against an adversarial database editor: existing canonical AEAD does not provide it. Startup full reconstruction is a useful recovery check but alone would not detect a membership row lost after startup, hence the cold-path completeness contract above.

## Required proof before release

1. Differential tests against the existing full-history reducers after each randomized public operation, including fractional rates, zero rates, overflow, inserts/replays/replacements/deletes and ownership changes.
2. Late/future observations, expiry-minus-one-nanosecond settlement, monthly clamp/anniversary/fixed-day/no-reset windows, manual and future resets, reversed arrival times, and unchanged-window quota/rate updates.
3. Every mutation seam above: success, failure and rollback. A deliberately raw tracked SQL write must trigger rebuilding before a new reader can admit. Canonical evidence and derived summaries cannot commit independently.
4. Independent Store handles and subprocess writers contend for last quota byte, IP slot and connection slot; ledger ingestion races admission; projection invalidation is durable across reopen/crash. Existing immutable/replay behavior remains unchanged.
5. Release versus final, finite zero outstanding, nonfinite unclosed, unresolved expired reservations across cycle changes, reviewed finalization, and rejected anomalies. Many closed historical budgets/leases do not enlarge warm working sets. Many unresolved budgets still deny without being forgotten. Repeated release/new-presence with unlimited and zero-rate budgets demonstrates that relevant live budget count can exceed 4096; measure this honestly and verify no obligation is discarded.
6. Service/group preview/apply, first assignment with historical policy, rejected calendar/quota/rate reductions, and rolled-back preview never change the effective accounting result.
7. Both old backup formats, fresh restore, different destination key, dirty reopen, corrupted/missing derived rows, unsupported derived version, interrupted migration, archive cancellation/limits and logical digest equality. Unknown physical tables remain rejected.
8. Re-run opt-in scaling with unrelated and same-account ledger history, current-window and older facts, closed budget/lease history, reopen/cold window transitions, realistic settlement writes and concurrent renewal. Measure warm latency, cold rebuild time, writer wait, DB/WAL growth and backup duration separately. Do not replace correctness tests with a millisecond SLA on a shared host.

## Cost and limits

This concentrates complexity in one private derived-state module plus central mutation plumbing; no new dependency, external service, endpoint, scheduler, or operational cache is needed. SQLite already supplies WAL snapshots, transactions, uniqueness, B-tree account lookups and triggers. It cannot transparently SUM application-encrypted fields or safely use floating-point/64-bit SQL arithmetic for exact weighted numerators.

An isolated implementation is plausible after the aggregate gate, but it should be split into separately reviewed changes: mutation/dirty plumbing and restore compatibility first; exact usage projection without a membership index second; live lease/reservation state third (subject to the reservation boundedness caveat). An account membership index is an optional later cold-path improvement, not a dependency of the ledger slice. The first change is the largest audit surface. Do not merge a projection-only shortcut first and hope to discover missing writes later.

Cold rebuilds, full-history backup/key verification, policy-collection scans, relevant outstanding-budget growth, and canonical disk growth remain real costs. For a small fleet, occasional canonical-ledger cold rebuild and linear backup may be a reasonable initial trade, to be measured; an optional verified account index can reduce cold scope later; ordinary renewals repeating lifetime decryption are not. If a strict lifetime-independent bound on cold requests is required, keyed time-bucket ledger indexes/aggregates and indexed policy metadata are additional design work. There is no safe tiny patch that simultaneously provides that stronger bound, preserves all encrypted metadata, and covers today's generic mutation/restore interfaces.

### Review correction: reservation boundedness

Independent review identified the release/churn counterexample above. The ledger-first slice still removes both unrelated and same-account settled ledger scans. The live-state follow-up removes closed lifetime history but is **not** independently bounded by the presence cap. Release-churn measurements and a deliberate decision about acceptable outstanding-budget working-set size are required before calling the complete admission path bounded or sustainable. No production change is authorized by this design note.

### Agreed minimal first slice after independent review

Implement only one lazily rebuilt encrypted usage window per account, transactional old/new ledger deltas, durable dirty triggers, and derived-schema/crypto/restore initialization. Do not add membership indexes or change lease/budget/hold/rate queries in this slice. A dirty fallback invalidates all account usage windows in the same transaction before clearing its marker; missing windows reconstruct from complete canonical history. Historical `Usage` may remain unchanged. Both root and independent security reviewer agreed this is the safer initial maintenance scope. It removes warm ledger-history dependence but deliberately retains global cold scan and other admission-history costs.

First-slice trigger scope is **only canonical `ledger`**. An UPDATE must match either OLD.kind or NEW.kind so kind/owner movement invalidates correctly. Ordinary lease/budget changes must not dirty usage windows. `RecordMeter` replay and rate reads belong after its SQLite writer reservation. Admission settlement must still commit through the existing denial closure even when renewal is denied; error/rollback/anomaly commits retain their current behavior. Read-only export must never initialize or rebuild projections.
