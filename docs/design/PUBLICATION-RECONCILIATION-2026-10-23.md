## Original source failure and proposed public seam

ServerRoutes generic publish failure preserves reviewed check/consents and permits another call. publishServer generates new per-instance revision and operation tokens each call, and the multi-target generation transaction advances every target generation. Same-deployment ownership permits deliberate republish, so unchanged fingerprint is not idempotency. Lost response after successful commit followed by generic retry can create another generation and a new lease. Latest `/agent/instances/{id}/state` cannot attribute an unknown request: it reports latest desired state. Operation-specific observations exist internally for Fleet, but there is no direct-publish actor/request receipt.

Relevant seams: server_deployments.go publishServer; store/generation_records.go CompareSetsAndGenerateRecords; instance_ownership.go prepareInstanceOwnership; agent.go state; agent_observation_history.go; existing route-exit-receipts implementation. The store transaction already supports arbitrary associated writes atomically with generations, desired records, manifests and ownership. No new job model/store primitive needed.

## Wire contract

Existing POST `/server-deployments/{id}/publish` gains required bounded `operationId` alongside exact existing input (`leaseSeconds`, `accessAllowed`, `quotaCertain`, `expectedFingerprint`). Name is an administrator request identity, NOT one of the generated per-target agent operation identities. An explicit new reviewed application gets a new ID; reconciling the same submission keeps the exact ID and exact immutable input.

Durable outcome union, HTTP200:
- `{operationId,deploymentId,status:"publication-accepted",nativeChecked:false,instances:[{instanceId,generation,operationId,revisionId}]}`. Generation remains decimal string. This acknowledges atomic queue acceptance, never application or traffic. Store full safe result in receipt; replay byte-equivalent semantics, with original lease issuance/expiry not renewed.
- `{operationId,deploymentId,status:"definitively-rejected",nativeChecked:false,code,detail}`. Allowlisted safe code/copy only; no generation consumed, no desired/manifest/ownership writes for this operation.

No new raw artifact/private digest/IR/key/credential in result. Existing frontend does not need artifact digest for acknowledgement; return only allowlisted identities. If legacy response fields must remain during migration, keep `id` as alias, not a second state model. Mandatory request ID avoids preserving the unsafe legacy retry path; update all intentional publish callers/tests. Historical pre-feature requests cannot retroactively gain receipts.

## Durable arbitration

Receipt key scoped by authenticated actor+operationId, stored body actor/deployment/purpose-separated HMAC of complete canonical request (excluding operationId) and terminal result. Reuse Store.ReviewToken with new purpose; no auth/key setup. Current requireAdmin runs first. Crossactor never reads another receipt; same actor ID reused for other deployment/input is a safe409, never a fresh publication or receipt disclosure.

1. Decode/validate envelope, authenticate, compute exact binding.
2. Look up matching receipt BEFORE current deployment/fingerprint/inventory/enrollment validation. A previously accepted receipt remains recoverable after draft drift, expiry, or later deliberate publication.
3. If absent, preserve ALL existing render/TLS/enrollment/ownership/public-route proof/CAS. Add receipt-absence compare.
4. In existing CompareSetsAndGenerateRecords callback, construct safe result from the exact allocated generations and generated per-target identities; append receipt write to desired/manifests/ownership writes. Transaction failure consumes no generation. No separately reserved receipt or precommitted request job.
5. CAS loser rereads authorized exact receipt before generic conflict. Concurrent identical callers return the same terminal outcome.
6. Proven nonretryable domain refusal can claim a rejected receipt via same receipt-absence CAS. Original prepared success compares that absence too, so either accepted or rejected wins, never both. Loser returns exact winner. Rejection persists even if baseline later restores; new action needs fresh explicit review/new ID.
7. Storage/read/decode/randomness/auth/unknown commit errors do NOT claim rejection. A failed/uncertain commit first attempts exact receipt recovery, otherwise remains unknown.

Baseline classifier hazards addressed in the isolated implementation: verifyServerInventory previously collapsed all reads into mismatch; enrollment reads were combined with unavailable409; verifyServerTLSArtifacts mixed store/list/host-read errors with pure TLS refusals; preparePublishedManifest mixed dependency errors and path refusal. Preserve operational errors and mark only completed domain refusals. HTTP422/409 alone never proves durable-safe failure. No renderer/private error strings in receipt.

## UX contract

Synchronous single-flight ref before starting the request, not just asynchronous React mutation/loading state. Freeze operation ID, deployment, checked fingerprint, exact consent/lease values. Generic network failure must not turn the primary action into an ordinary new apply.

Unknown state offers one explicit action to resume/reconcile this same request and permits dismissal without abandoning its identity. Replaying POST may enqueue the originally authorized submission if it never reached the server; label it accordingly (e.g. 恢复本次提交), not as a purely read-only status refresh. Do not automatically retry or silently change inputs.

Keep pending envelope outside the keyed detail/modal so revision refresh and safe close/reopen do not lose it. Prefer actor/session-scoped workspace memory consistent with current source-receipt owner scope; never persist TLS or IR. On account switch hide old operation and do not replay under another actor. Full browser reload/crash recovery is an explicit scope decision: either persist a nonsecret exact envelope in actor-scoped tab session storage, or state the in-memory boundary honestly. Do not claim reload recovery without implementing/testing it; no automatic submission on restoration.

Only validate a matching terminal union (operationId/deploymentId/status and required result fields) before unlocking. Accepted closes review, refreshes existing instance status, says 已提交/等待实例确认. Rejected clears check/consents and offers explicit reload+fresh review while preserving useful local nonauthorization choices. Malformed response, mismatched IDs, generic401/403/409/500 remain unresolved, never silently allocate new ID. New publication after acceptance is a separate explicit review, not a replay button. Existing per-instance observations remain distinct from immutable queue acknowledgement.

## Public RED and acceptance seams

1. Characterization RED without new wire field: use current authenticated fixture; validate once, POST exact accepted body twice (discard first UI response). Public second generation differs; desired invariant is no second generation for one stable request. Then new-contract RED sends operationId (current strict decoder rejects it), followed by implementation acceptance. Do not call either observed until run under QA authority.
2. Local HTTP transport/proxy drops only first response AFTER real handler commit; retry same ID/body returns identical accepted receipt. GET existing instance state confirms unchanged generation/revision/agent operation. No native process.
3. Concurrent identical requests: one generation per target. Success-vs-rejected receipt race: only winner writes; rejected winner consumes none. Public store transaction seam can prove already-prepared commit fence without production scheduling hooks.
4. Lost definitive failure, input drift/restoration, same ID: immutable rejected outcome; new ID requires fresh review. Operational read/decode failure then repair: same ID can still accept, no rejection tombstone.
5. Exact binding changed fingerprint/lease/consent/deployment refuses; another admin never gets original receipt; regular user403. Accepted replay after later generations returns original receipt, not current state.
6. Existing CAS, foreign ownership, enrollment and packaged-TLS failures remain enforced. Do not weaken validation to make repeat succeed. Backend restart retains receipts (same store master); no early eviction that would permit ID reuse.
7. UI real click double-submit/keyboard, lost response, modal close/reopen, changed draft while unknown, rejected outcome fresh review, malformed/mismatched receipts, auth change. Preserve P1 stale-render/reload tests. Browser evidence synthetic API unless separately actual local backend; no applied/traffic claim.

## Root decision 14:37 UTC (supersedes open persistence choice)

Implementation authorized only AFTER P1 canonical integration. Use bounded actor-scoped tab sessionStorage containing a versioned exact nonsecret request envelope (actorId, deploymentId, operationId, fingerprint, lease/ack fields). Treat restored bytes as untrusted; validate exact supported shape, bounded IDs/size/value types/ranges; wait for verified same actor and current permission. Never auto-submit/replay. Clear on logout/account switch and matching terminal resolution. Detail close retains task. No IR, TLS, material, credentials, CSRF token or raw records in storage.

Add a minimal read-only authenticated GET `/server-deployments/{id}/publication-requests/{operationId}`. It returns only same-actor deployment-matched receipt, safe outcome, and echoed exact nonsecret request fields; client compares every echoed request field with the frozen/restored envelope before accepting outcome. POST retains server HMAC binding. No fingerprint/flags in URL and no separate client hashing scheme. Missing receipt404 proves only that no receipt was read at that instant, not that an in-flight original cannot commit; keep unresolved and offer explicit same-ID exact retry. GET does not reserve identity, write a tombstone or advance generations. Crossactor lookup must not disclose another actor's receipt. Scope this as one request receipt lifecycle, not another job framework.

Additional acceptance: malformed/oversized/unsupported-version storage never posts; changed actor/permission never auto-loads another identity's operation; logout clears tab state; reload same actor presents explicit reconciliation, GET absence remains unknown, exact retry keeps ID; changed request echo or outcome IDs cannot resolve uncertainty. A terminal rejected record requires fresh explicit review before allocating a new request. Operational lookup failure preserves pending handle.

## Approved precision/edge decisions 14:49 UTC

GET exact body is `{request:{leaseSeconds,accessAllowed,quotaCertain,expectedFingerprint},result:<terminal union>}`; never echo arbitrary original JSON. POST returns terminal union top-level. IDs follow existing domain.ValidID1–64 regex; fingerprint64 lowercase hex; lease integer30–3600; acknowledgements boolean. Accepted generation is canonical positive decimal STRING <=9223372036854775807, not a JS numeric value; clients compare without rounding. Accepted instances must be nonempty and instance IDs unique; no arbitrary new target-count cap absent an existing backend limit.

Rejected code allowlist: `SERVER_DRAFT_CHANGED` or `PUBLICATION_REJECTED`; detail is a fixed actionable domain-safe message, never raw error/stringified private input. Preserve operational errors rather than guessing from HTTP status.

First sessionStorage write failure blocks the first POST and reports a retryable local recovery-record problem. Terminal removal failure does not reverse an adopted known outcome: retain terminal state in memory, show local cleanup issue, never resend automatically or claim storage cleared. Pending continue-link honors existing workspace dirty guard. Missing verified controller visibly disables application with an honest reverify/unavailable state, not a fake actor or enabled dead action. Production verified actor/current permission come only from App session lifecycle. Clear terminal envelope only after result safely adopted/displayed. Approved source work still waits for P1 canonical integration.
